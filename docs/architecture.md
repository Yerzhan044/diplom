# Архитектура MVP

## Поток данных

1. Источник транзакций (симулятор или внешний процессинг) отправляет событие в API.
2. API собирает online-признаки (velocity и отклонение от среднего чека).
3. Гибридный скоринг:
   - Rule Engine (бизнес-правила)
   - Ensemble ML-модель (soft voting вероятность fraud)
4. API возвращает решение: APPROVE / REVIEW / DECLINE.
5. Событие решения логируется для аналитики и ретрейна.

## Компоненты

- `app/main.py` — FastAPI сервис с endpoint для real-time скоринга.
- `app/model.py` — загрузка модели и предсказание вероятности.
- `app/rules.py` — explainable правила (человекочитаемая причина).
- `app/state.py` — in-memory online-агрегаты по карте.
- `train/train_model.py` — генерация синтетики и офлайн обучение ensemble-модели.
- `simulator/generate_stream.py` — потоковая генерация транзакций.

## Почему такой дизайн

- Быстрый запуск и демонстрация диплома на одном ноутбуке.
- Прозрачность решений (правила + вероятность + причины).
- Можно легко масштабировать (Redis/Kafka/PostgreSQL) на следующем этапе.

## Связь с дипломной структурой

- Глава 1: обоснование отказа от rule-only подхода и необходимость адаптивного ML.
- Глава 2: текущая архитектура real-time пайплайна (этот документ).
- Глава 3: реализация ensemble-обучения и оценка метрик.
- Глава 3: explainability через человекочитаемые причины срабатывания правил.
